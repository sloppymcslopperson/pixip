`/`, `/command args`, `!cmd` and `!!cmd` must behave like Pi's TUI from the pixip composer. This slice owns the prefix classifier, the shared command registry/policy (whitelist/blacklist), bash execution, and the prompt/steer dispatch that keeps extension commands working while busy.

### Why now

The owner needs TUI parity to move pixip development into pixip itself (dogfooding): the command surface comes before the rest of the backlog. This is slice 1 of the next leg; the other slices are `05-builtin-commands`, `06-command-menu`, `07-queue-display`, and `08-session-commands` (re-scoped from `backlog/70`). `docs/parity.md` tracks the full TUI surface.

### Goal

- One deep, DOM-free module owns parsing, the command catalog, and the policy; menus/notices/handlers consume it instead of keeping parallel lists.
- `!`/`!!` run through the RPC `bash` command, stream into a card, and `!!` is excluded from model context.
- Slash input is classified into: pixip built-in (handled by `05`), Pi extension/template/skill (passthrough), Pi TUI-only (local notice), or unknown (passthrough, exactly like the TUI).
- Slash input while busy goes through `prompt` with `streamingBehavior: "steer"`, so extension commands still execute immediately and templates/skills queue.

### Done when

- `src/client/commands.js` (pure, no DOM) exports `classifyInput()`, the built-in + TUI-only catalog, `resolvePolicy()`, and `visibleCommands()`; covered by `test/commands.test.js`.
- The hub resolves a per-session policy from three layers (data-dir `pixip.json`, the session cwd's `.pixip.json`, CLI flags), validates it, and sends it to the client; the merge is restrict-only.
- `!cmd` and `!!cmd` send a `bash` frame with a client-generated id; `bash_execution_update` events stream into the matching card; a final `bash` frame carries output, exit code, cancellation, truncation and full-output path. `!!` sets `excludeFromContext` and shows an `excluded` badge.
- `!`/`!!` with no command is a no-op; bash is allowed while the agent is streaming (one at a time); plain text keeps its current idle/busy dispatch.
- `/extcmd`, templates and skills still work while busy (proven with a fake Pi that logs `streamingBehavior`).
- TUI-only commands and denied commands produce a local notice and are never sent to the model.
- `npm run check` green; `docs/parity.md` updated for every command this slice touches; `ARCHITECTURE.md` gains the `bash` frame and the `prompt` `streamingBehavior` note.

### Decisions (grilled 2026-11-21)

- Mapping: `!cmd` -> bash `excludeFromContext: false`; `!!cmd` -> `true`. Classification trims like the TUI: the bang check is on the trimmed line, the command text after the bang is trimmed. No escape for a literal leading `!` (same as the TUI).
- Rendering: create the card on submit (optimistic), append `bash_execution_update` deltas, then annotate/replace with the final result (exit code, cancelled, truncated, full-output path); no separate user echo line (TUI shows only the bash card). Empty output still shows the card.
- Busy: bash is allowed while streaming; the RPC `bash` command queues its message for the next prompt. One bash at a time (TUI guard: while `isBashRunning`, refuse with a toast).
- Slash input while busy uses `prompt` with `streamingBehavior: "steer"` instead of the current separate `steer` command. Plain text may keep using `steer`.
- Abort-running-bash is **not** in this slice (deferred; listed as a gap in `docs/parity.md`).
- Config: all three layers, merged restrict-only so a more specific layer can only narrow:
  - `deny` = union of all layers' names;
  - `allow` = intersection of the non-empty `allow` lists (an empty list means "no allow restriction");
  - `bash` = AND of all layers (a `false` anywhere disables `!`/`!!`);
  - `deny` wins over `allow`; names are bare (`compact`, not `/compact`); command-level granularity only (no per-source filters).
  - Files: `<data-dir>/pixip.json` and `<session-cwd>/.pixip.json`, section `{"commands": {"allow": [], "deny": [], "bash": true}}`; unknown keys are reported, malformed JSON is a startup error with the file path. CLI flags: `--allow-command <name>` (repeatable), `--deny-command <name>`, `--no-bash`.
  - Read once per session at attach (hub restart/reconnect to reload), resolved against the session's cwd, and sent to the client as the effective policy.
- Deep module: classification/catalog/policy filtering live in one pure client module; the hub side is only "read + validate + merge + serve" so the surface stays small.
- Unknown `/thing` that is not a built-in, TUI-only command, extension command, template or skill is sent to Pi as a prompt (the TUI does the same).
- The `bash` id is generated by the client and passed through the hub to Pi, so `bash_execution_update.id` matches without parsing event payloads.
- Policy is per session (cwd-dependent); the list view does not need it.

### Extension commands (`/fit` and every other extension command)

No pixip-side dependency: `/fit` is a Pi extension command (`pi.registerCommand("fit")` in the `FIT_pi` package), so forwarding the literal slash text to Pi's `prompt` is the whole integration. The owner coordinates development with `/fit`, so this slice must guarantee the following for extension commands generically:

- Forward slash text verbatim (arguments preserved; only the composer's outer trim). No built-in/catalog match means passthrough to `prompt`.
- While busy use `prompt` with `streamingBehavior: "steer"` (already decided). RPC `steer` does **not** execute extension commands — it expands skills/templates and queues text — so `/fit` while streaming would otherwise be queued as a literal prompt and never run.
- Do not apply the 20 s `RpcChild` timeout to `prompt`: extension handlers legitimately block on `ctx.ui.select`/`confirm`/`editor` (the FIT human workflow does), so the prompt response can take minutes. Give prompt a long/no timeout (configurable for tests) and treat a late or failed prompt response as advisory rather than an error toast.
- `notify` with multi-line or long text must be readable: open a dismissible sheet (or an expandable toast) instead of the current 3.2 s toast. Verified real-Pi: `/fit help` sends a 2295-character notify; a toast is useless for that.
- `extension_ui_request` methods pixip does not implement (e.g. `setStatus`) stay ignored, as today; dialogs (`select`/`confirm`/`input`/`editor`) are answered from the phone through the existing sheet.
- Policy stays uniform: extension commands are allowed by default; `allow`/`deny` may name `fit` like any other command; nothing in the built-in/TUI-only catalog special-cases it.
- Tests: the fake Pi emulates an extension command (long `notify`, a `select` dialog, a prompt response delayed past a test-configured short timeout); assert the prompt text arrived verbatim, one dialog and one readable notify, and no error frame. Real-Pi smoke already done for `/fit help` (2026-11-21: notify + successful prompt, idle); repeat for `/fit list` and a dialog-driven `/fit edit` once the timeout work lands.
