  - `deny` = union of all layers' names;
  - `allow` = intersection of the non-empty `allow` lists (an empty list means "no allow restriction");
  - `bash` = AND of all layers (a `false` anywhere disables `!`/`!!`);
  - `deny` wins over `allow`; names are bare (`compact`, not `/compact`); command-level granularity only (no per-source filters).
  - Files: `<data-dir>/pixip.json` and `<session-cwd>/.pixip.json`, section `{"commands": {"allow": [], "deny": [], "bash": true}}`; unknown keys are reported, malformed JSON is a startup error with the file path. CLI flags: `--allow-command <name>` (repeatable), `--deny-command <name>`, `--no-bash`.
  - Read once per session at attach (hub restart/reconnect to reload), resolved against the session's cwd, and sent to the client as the effective policy.
- Deep module: classification/catalog/policy filtering live in one pure client module; the hub side is only "read + validate + merge + serve" so the surface stays small.
- Unknown `/thing` that is not a built-in, TUI-only command, extension command, template or skill is sent to Pi as a prompt (the TUI does the same).
- The `bash` id is generated by the client and passed through the hub to Pi, so `bash_execution_update.id` matches without parsing event payloads.
- Policy is per session (cwd-dependent); the list view does not need it.

pixip can run as a managed background daemon and refresh itself: a soft reload of assets, command policy and the session index without touching live children, and a hard restart that survives via JSONL. This is what lets the agent edit pixip and pick up its own changes mid-session, and lets the user keep pixip up across shells.

Without this, every hub change means killing the process by hand mid-session.

### Done when

- `pixip start|stop|status|logs|refresh|restart` subcommands; bare `pixip` keeps serving in the foreground exactly as today. Pid, log and control state live under `<data-dir>` (`pixip.pid`, `pixip.log`), so `--data-dir` stays the isolation boundary and tests never touch a real daemon.

- Hard refresh (`pixip restart [--force] [--when-idle]`): replaces the process. Sessions survive as JSONL and reattach on open; refuse while any session is busy unless `--force`; `--when-idle` waits (bounded, default ~5 min) for all sessions to be idle and exits non-zero on timeout. - **Loopback guard scope:** `POST /api/refresh` only. `POST /api/sessions` and the
  stop route keep today's posture (the UI has no auth either way; this is not an
  auth change).
- **New modules are allowed** where they keep `bin/pixip.ts` thin: a
  `src/daemon.ts` for pid/state/detach/control helpers plus test helpers, and
  client changes stay in `app.js`/`index.html`/`style.css`.
- **Assumption:** soft refresh re-reads the session index *and* broadcasts a fresh
  `sessions` frame to list sockets, so the list is correct even before the page
  reload; the UI reload action still reloads the page afterwards.

Entries that arrive between `get_entries` and the subscription are lost, so a client connecting mid-turn can miss the start of a message. Subscribe first, buffer, and reconcile with Pi's durable entry cursor.

### Goal

No lost or duplicated entries across the snapshot/live boundary, using Pi's durable entry cursor.
